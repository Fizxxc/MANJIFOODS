## 2026-10-31 P0: QRIS/order read failures

### Audit, reproduction and plan

Read the required project contracts, current migrations, data/report routes, checkout/payment RPCs, React consumers and test fixtures. Plan: reproduce the exact read failure; normalize/validate the shared payment read model; correct query/error handling and QRIS failure states; test role/data-integrity boundaries and compile production. No unrelated UI redesign, dependencies, checkout RPC changes or database migration.

**Exact cause:** `001_initial_schema.sql` declares `payments.order_id UUID NOT NULL UNIQUE REFERENCES orders(id)`. PostgREST correctly treats this reverse relationship as one-to-one and returns an object or null. `/api/data` treated it as an array in the proof-ID `flatMap(...payments.map(...))`. The exception was passed to the generic API error helper, which classified it as HTTP 400 and echoed its message. Therefore a valid `page=0&order=<uuid>` failed after successful checkout, and the browser displayed the minified `a.payments.map is not a function`. React indexed that object as an array and reports silently missed its payment status. Array-only fixtures had hidden the production cardinality. The manual-session migration does not alter this payment relationship.

Added a failing regression before the fix: real data route + mocked PostgREST OBJECT embed returned 400 where 200 was expected. Then changed the read boundary, not database cardinality or stored records. PostgREST's documented one-to-one behavior: https://docs.postgrest.org/en/v13/references/api/resource_embedding.html . Static QRIS amount entry contract: https://www.bi.go.id/id/fungsi-utama/sistem-pembayaran/ritel/kanal-layanan/qris/default.aspx .
