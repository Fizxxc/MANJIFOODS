# Security model

- Auth: Supabase Auth + SSR session; email verification/password recovery as configured; no self-assigned admin and no plaintext remembered passwords.
- Login, registration and recovery use POST bodies. Native HTML forms explicitly use `method="post" action="/api/auth"`, so a hydration failure cannot submit credentials by GET. The same bounded validators and origin checks apply to JSON and URL-encoded forms. Native responses use 303 redirects with fixed status codes, never submitted fields. The proxy strips legacy credential query parameters before rendering; the client also replaces any remaining credential URL. Existing upstream logs/history cannot be retroactively erased by this fix.
- CSP has one owner: `src/proxy.ts`, using `src/lib/csp.ts`. It overwrites incoming CSP/nonce headers, generates a fresh nonce per request and forwards that same policy to Next rendering and the browser, including after session refresh. All HTML renders dynamically; no cached HTML may reuse a nonce. Static resources retain their cache policy and skip auth refresh, while still receiving CSP. Do not add a second CSP in `next.config.ts`, a meta tag or the hosting layer: browsers enforce every policy together.
- Production scripts use a nonce and `strict-dynamic`, block inline event handlers, and allow neither `unsafe-eval` nor unrestricted inline scripts. Development alone permits `unsafe-eval` for Next/React debugging and the exact dev-server WebSocket origin for Fast Refresh. Inline styles remain permitted for React/Next loading styles. Objects, frames and framing are blocked; forms are same-origin; backend HTTP/WebSocket connections use the configured Supabase origin without wildcards. `Referrer-Policy: no-referrer` prevents query strings from being forwarded in Referer headers.
- Workers are same-origin only: the application registers `/sw.js`; Supabase's optional blob heartbeat worker is not enabled and this webpack development client does not require it. `blob:` is not allowed in script/worker sources. If a future dependency requires a worker, prefer a same-origin worker file and review that exact use before changing the policy.
- DB: RLS enabled on student-exposed tables; students view only their profile, cart, orders, order events, notifications and push subscriptions. Product/category/availability public read subject to policy. Restricted payment verification writes server-only.
- Admin: use `SECURITY DEFINER` role-check function with locked search_path, and only grant EXECUTE of sensitive transitions to trusted actor; do not assume frontend guard protects actions.
- Checkout: transaction + SELECT FOR UPDATE/advisory lock as appropriate, idempotency unique key by student, immutable snapshots, server price and quantity validation, atomic stock/slot reservation.
- Uploads: private bucket, short-lived signed URL after authorization, max size/MIME whitelist and limit; do not expose student payment screenshots in public.
- API: Zod validation, per-user/per-IP rate controls, no broad SQL exposure; verify CSRF/origin protection for cookie-authenticated mutation endpoints. Keep Supabase keys and VAPID private keys server-side.
- Realtime: filtered/private subscriptions or authorized refetch via event topics; never broadcast full other students' order payloads.
- Safe status transitions, audit log append-only for student and admin operations. Don't write PII or secrets to console logs.
- Push: avoid lock-screen personal information, remove expired subscriptions and honor opt-out.
- Threat tests: student changes another order, student attempts role escalation, forged price/quantity, duplicate checkout, double admin verify, forged payment proof, disabled product, sold-out race, slot overbooking, invalid file upload, unauthorized proof retrieval.
